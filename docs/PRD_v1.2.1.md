# Token BI 1.2.1 迭代需求与原型

日期：2026-09-14。基线：已发布的 1.2.0。目标版本：1.2.1。

**状态：用户已验收 HTML 原型并授权开发、推送 GitHub。本轮实施与验证见 [技术纪要](TECH_v1.2.1.md)；下方保留原型阶段的讨论依据。**

## 来源与范围

来源：用户确认先以 HTML 演示以下三项迭代，原型无误后再开发。

1. 首次安装后以菜单栏附近的轻提示告知入口，文案“我在这里哦”。
2. 在设置中检查和执行更新，发现新版本时在底部设置显示小红点。
3. 检阅代码，清理冗余或无效内容，精简安装包。

沿用现有 311px 菜单栏面板、账号与额度样式及扫码副屏入口。不更换桌面技术栈，不恢复旧控制台，不调整额度计算或数据源优先级。

### 菜单栏面板交互（2026-09-14 用户确认）

- 删除“保持面板展开”开关和所有子页面右上角图钉，不保留固定面板模式。
- 单击菜单栏图标展开，再次单击收起。
- 点击面板外的桌面、其他软件窗口，或通过键盘切换窗口导致失焦时，面板自动收起；不抢回焦点。
- 主页、设置、二维码与诊断页执行相同规则，不因页面不同而保持展开。
- 单纯把鼠标移出面板不等同于切换窗口，不触发收起，以免影响阅读或扫码。
- 面板收起不停止本地服务、额度同步或已开始的更新下载。任务完成不自动重新展开面板；用户再点图标查看结果。
- HTML 原型使用外部点击、焦点移出、窗口 blur 及页面隐藏事件模拟。正式开发时需在原生窗口层实现并验证失焦收起，同时移除原固定状态及控制入口，不能只隐藏按钮。

## FR-01 首次运行引导

### 用户体验

首次安装后**第一次打开 App**，在菜单栏图标完成创建和定位后展示小型气泡，而不是在拖拽 DMG 安装时展示。

- 标题：我在这里哦。
- 正文：Token BI 已常驻菜单栏。点击上方图标，查看额度或扫码连接副屏。
- 操作：打开 Token BI、知道了、关闭。
- 点击图标或“打开 Token BI”进入现有额度面板；另外两项关闭提示，服务继续运行。
- 无全屏遮罩、独立启动页或强制倒计时。提示不依赖账号或 usage 请求成功。
- 建议确认/关闭后记住完成状态，不在每次启动重复提示；设置中的业务选项不被引导重置。

原型仅在自己的 localStorage 命名空间记录是否看过提示。通过“首次启动 / 重新演示”可重复验收，不改变真实应用偏好。

### 已采纳的实施决策

- 1.2.0 老用户升级后也提示一次：仅对未完成过引导的安装展示，不按版本反复弹出。
- 原型模拟“贴近图标”的视觉，不代表已完成原生窗口定位验证。研发阶段验证不同缩放、多屏、菜单栏自动隐藏及图标被隐藏时的可发现性；无法取得可靠锚点时不能把提示放到屏幕外。
- 系统入口统一称为 macOS“菜单栏”；该气泡不是通知中心推送，不以系统通知授权作为可发现入口的前提。

### 验收

- 首次打开可通过提示找到图标，打开面板并找到扫码入口。
- 确认、关闭或直接打开面板后，再次启动不重复提示。
- 引导与登录、同步、服务就绪解耦，网络失败不阻塞菜单栏出现。
- 多屏和缩放条件下锚点正确，不闪现错误宽度或遮挡整个桌面。

## FR-02 应用内更新

### 交互规则

- 进入设置，在诊断信息之后增加“软件更新”，显示当前版本和检查状态；不再展示固定面板偏好。
- 未发现更新时按钮为“检查更新”；点击后禁用重复操作并显示“正在检查”。
- 联网且后台发现高于当前版本的更新时，底部设置图标右上角出现小红点；不自动展开面板、不弹抢焦点通知。
- 进入设置后按钮为“立即更新”，可展开版本说明。
- 建议红点在**成功安装**前保留：进入设置或选择稍后不代表更新已完成；同时提供可访问名称“设置，有新版本待更新”，不单靠颜色传达状态。
- 点击立即更新开始应用内下载，显示进度；可返回额度，下载继续。
- 校验通过后按钮变为“重启完成更新”，明确说明副屏会短暂断连。此按钮是安装重启的用户确认，不自动强制重启。
- 更新后显示新版本、清除红点、恢复原有本地服务和副屏连接。

### 状态与失败处理

| 状态 | 用户可见反馈 | 可用操作 |
| --- | --- | --- |
| 未检查 | 当前版本、尚未检查 | 检查更新 |
| 检查中 | 正在连接更新服务 | 避免重复请求 |
| 无更新 | 已是最新版本、上次检查时间 | 再次检查 |
| 有更新 | 新版本、可展开更新说明 | 立即更新 / 稍后 |
| 下载中 | 进度 | 返回额度，后台下载 |
| 已就绪 | 包已校验、重启影响 | 重启完成更新 / 稍后 |
| 检查失败 | 网络或服务失败原因 | 重新检查 |
| 下载中断 | 保留旧版本、说明原因 | 重新下载 |
| 校验失败 | 阻止安装、旧版本可继续使用 | 重新下载，无跳过校验 |
| 更新成功 | 新版本、服务恢复 | 返回额度 |

原型覆盖上述主要状态。生产实现还需区分超时、HTTP/版本清单异常、磁盘空间不足、安装权限或替换失败，避免全部误报为“断网”。

### 技术实施边界

- 采用 [Tauri 官方 Updater](https://v2.tauri.app/plugin/updater/) 和 GitHub Releases 静态版本清单。
- 现有依赖和 endpoint 不等于功能已启用：需注册插件、替换占位公钥、生成更新包和签名，接通 UI 与发布流程。
- 首期全量更新，不承诺增量包；客户端不包含发布令牌或签名私钥。
- 公钥随应用分发，私钥安全保存并备份。Updater 签名和 Apple 应用签名/公证独立规划。
- 后台检查建议在应用就绪后非阻塞执行，启动检查加 6 小时间隔；失败退避、同一时间只允许一个检查任务。间隔待确认，不在首屏加载路径加入网络等待。
- 手动检查立即执行，不要求用户等待定时任务。无网检查失败不影响额度展示。
- 已发现的新版本信息与“最近检查失败”分开保存，后续一次检查失败不能清除已知待更新提醒。
- 只有安装前才有序关闭当前应用拥有的 control/backend 进程。下载和检查阶段保持服务运行，不清理其他实例或用户 Codex 进程。
- 升级保留 Application Support 下的用户数据、账号偏好和引导状态；安装失败给出恢复路径，不伪报成功。
- 重启后恢复服务；已打开的副屏通过现有重连机制恢复。新增页面版本检测方案需避免刷新循环，UI 更新不等同于接口数据轮询。
- 正式发布前完成包、签名、平台键和版本清单匹配验证，资源完整后才使新版本可见。仅 git push 源码不会触发客户端更新。
- 现有 1.2.0 用户需手动安装一次支持 updater 的版本；再用受控 N → N+1 升级验证真实闭环。

### 验收

- 手动检查、后台发现、红点、更新说明、下载、稍后、重启的状态对应一致。
- 返回额度或收起面板不重置下载；重复点击不会创建重复下载/安装任务。
- 断网、超时、坏清单、无效签名均不会破坏已安装版本，恢复网络后可重试。
- 签名失败绝不允许安装。只有校验通过且用户确认，才能进入替换/重启流程。
- 在真实已安装包上验证 N → N+1，确认服务退出和恢复、端口释放、账号偏好及副屏重连。

## FR-03 代码质量与包体精简

此项没有新增 UI，不在设置里添加“清理应用”“瘦身”等无必要的用户按钮。原型通过后再提交有依据的删减清单并实施。

### 本轮初步阅读依据

- `scripts/prepare_desktop.mjs` 已使用生产资源白名单，原型与测试未进入前端包；不能声称删除文档或测试即可缩小安装包。
- `src-tauri/tauri.conf.json` 同时携带 control 与 backend runtime；`scripts/build_sidecar.sh` 分别构建两个 PyInstaller onedir 产物。
- `token-bi-backend.spec` 使用 `collect_submodules("app")` 和 `collect_submodules("uvicorn")`，`token-bi-control.spec` 保留本地控制台模板。它们是依赖与入口审查候选项，不是已确认无用代码。
- Updater 将在本期接通，因此不能再将其简单当作未使用依赖移除。

### 优化顺序

1. 建立源码引用、动态导入、构建产物和启动入口清单，确认每个删除项的消费者。
2. 删除无调用包装、过期分支及重复实现；保留有行为断言的有效回归，不按测试数量裁减。
3. 检查静态资源、依赖与两个运行时的重复内容，评估是否可共享；不为包体数字贸然合并进程或破坏故障隔离。
4. 同一工具链测量 DMG、安装体积、启动耗时和常驻内存，再决定下一步。

### 基准与限制

- 1.2.0 已发布 DMG：68,186,865 字节，约 65 MiB。
- 2026-09-14 对现有本地构建目录执行 `du -sk`：control 11,132 KiB、backend 152,352 KiB、App 198,884 KiB。这是本地文件系统占用，不等于精确归档大小或未来用户设备上的安装占用。
- 启动与内存本轮未重新测量；不承诺尚未测得的性能收益或目标压缩比例。
- 保留 OAuth 优先、单账号语义、登出边界、进程所有权、签名校验、LAN/副屏恢复及横竖屏布局回归。
